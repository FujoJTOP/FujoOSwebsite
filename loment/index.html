首页 / Loment · Potato

Loment 管怎么写，Potato 管怎么看。

这不是两门语言在竞争。Loment 是语言：语法、类型、所有权、能力域。Potato 不是语言，是编译流程输出端的形式对象——无语法，只有结构。两者在语义模型处相遇。

读上手文档 (Beta)

先看波 C 测量

为什么不用“造一门新语言”作为起点 —— 痛点不在 Rust，而在同一个接口被 N 种语言各写一遍。换掉内核语言只会让 N 变成 N+1。
语法不新，语义才新 —— Loment 的表面语法取 Rust 的严格子集，大模型的 Rust 先验可以直接迁移，绕开“零语料”这道坎。

分工：写与看

作者面向 Loment 写系统；机器面向 Potato 读系统。编译器是两者的接缝——它为每一个编译单元强制导出形式对象，没有关闭的开关。

为什么不能把它俩合并

零语料的问题会回来。 语言要有语料才能被模型书写；表示层不需要语料，它消费结构。把 Potato 变成语言，等于把 Loment 拖回“世俗新语言”的陷阱。
它同时是唯一的战略保留地。 Potato 曾是项目刻意闭源的一层；现在决定全部开源，只是仓库尚未公开。规范与实现都可复现，论文三的测量因此更强。

L0 · 接口层：现在就能做的那部分

同一个事实在 JSON、Rust、C、Python 里各写一份——这是当前最实际的成本，也是十个痛点里七个的共同根因。L0 的做法是：一份 .lom 单一真源，生成器产出各类目标，一致性在生成期就被保证。

lom 单一真源：一处声明，多处生成 
// lom/fuc.lom — .fuc 节点布局，此前散落在打包器、内核与新文档三处
record FucNode layout(packed, size=64) {
  kind:  u16 @0
  flags: u16 @2
  x:     i16 @4
  y:     i16 @6
}

// lom/fuai.lom — 46 个契约原语与部署参数
enum Opcode: u16 {
  cfg_get = 0x8106 {
    sig: "a0=key", fujo: "fujo_cfg_get", linux: "fuai_cfg_get",
    semantics: "config read (defaults 1->50 2->0 7->45 8->35)"
  }
}

生成物：Rust 常量与解码器、C 头、Python 打包器、JSON 规范，以及一个漂移检查器。判据是漂移检查器可以退役——漂移在生成期就不可能发生。

L1 · 系统语言

设计目标按优先级排：布局与 ABI 是一等公民；确定性（无 GC、显式所有权、no_std 优先）；能力域语法化；每个编译单元导出可审计的语义模型；跨后端。第一版是 Loment → Rust 的转译器，不写后端——先拿到一个能跑、能与 Rust 原版逐位对齐的语言。

loment 能力域是语言构造，不是库调用 
// 作者面
capability blk_write: disk[0..4] revocable {
  on_revoke => fallback
}

export fn flush(req: FlushReq) contract(hex64) {
  guard blk_write(idx)   // 越界在编译期拒绝
  ...
}
json 机器面：编译器强制产出的形式对象 
{"unit": "ahci.flush",
 "potato": "v1",
 "capabilities": [
   {"name": "blk_write", "domain": "disk[0..4]",
    "revocable": true, "on_revoke": "fallback"}
 ],
 "contracts": [{"pred": "hex64", "mode": "binary"}],
 "guards": 1,
 "excluded": []}
版本 覆盖 校验
Potato v0 标量、数组、struct、枚举、布局、能力域 仍合法，可回放（冻结样本 demo.v0.json）
Potato v1 新增泛型与单态化实例、trait/impl、切片、str、ptr、()、guard 审计站点 7/7 自检 · 33 条反例全被拒 · 跨实现 50/50
强制导出的三层都不可关闭： 编译器内部有错即编译失败；CLI 层要 emit 目标就必须同时 emit 形式对象；仓库层要求每个示例都有逐字节一致的 .potato.json 并通过独立校验器。

已经闭环的几件事

  • 自举定点 —— 编译器编译自身；三阶段产物 IR 逐字节全等（1002385 B）。
  • 原生后端 —— LLVM IR 路径与 Rust 转译路径双路径差分，逐值一致；差分曾抓出真实的掩码 bug。
  • 工具链 —— lomfmt、LSP、包管理器、文档生成器、DWARF 语句级行表、增量构建（冷 82.6 ms → 热 9.0 ms）。
  • 内核内运行 —— Loment 用户态程序跑在 FujoOS 上；syscall 层由 .lom 生成，46/46 opcode 覆盖。

止损线写在前面

P2 若三个月内无法与 Rust 原版逐位对齐，就回退到“L0 + 代码生成”路线，L1 归档。这条线在立项文档里就写定了，而不是事后追认。

当时担心的两件事后来都过了：自举 parser 在全语料上与 Python 版逐字符一致（42/42），检查器的规则等价也到了 63/63。所以 L1 没有触发这条止损线。

波 C 测量：把“能转写”变成可复现的数字

语料是 12 个仓库真实文件（每语言 4 个），每个文件的 sha256 记入结果文件，测量与内容绑定。两臂是工具链的严格与宽松档——都确定性、可复现，不使用随机数。

识别率与转换率必须一起读——转换率是“条件于识别”的比率
语言 臂 实体 识别率 转换率 95% CI
Python 严格 48 100.0% 27.1% [16.6, 41.0]
宽松 48 100.0% 93.8% [83.2, 97.9]
C 严格 37 89.2% 100.0% [89.6, 100.0]
宽松 37 89.2% 100.0% [89.6, 100.0]
Rust 严格 116 98.3% 91.2% [84.6, 95.2]
宽松 116 98.3% 98.2% [93.8, 99.5]
  • Python 的瓶颈是注解质量 —— 严格臂 27.1%，主因是 list[str]/dict 这类没有 Potato 对应物的容器类型被跳过。
  • C 的瓶颈是识别器 —— 识别率 89.2%，4 个多行/宏签名对正则不可见；100% 的转换率不能单独引用。
  • Rust 最好转 —— 静态类型加显式切片；剩余跳过是常量长度数组、never 类型与元组返回。
  • 对象合法率 100% —— 工具链宁可少转，也不乱转。
一个必须标注的边界： 宿主 LLM 臂尚未运行（本环境没有外部模型凭据）。协议已就绪，任何外部转写器按同一报告 schema 产出结果即可并入主表——但当前主表的“两臂”不得在论文中当作 LLM 对照。
