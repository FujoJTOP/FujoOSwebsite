那一格为什么重要

在此之前，自举链只能从 Python 版编译器起步：stage1 由 tools/lomentc.py 现编。也就是说，“想重建 Loment 编译器”这件事本身依赖一个解释器。这条依赖比工具链（格式化、文档、语言服务）更根本 —— 它不在使用侧，在重建编译器那一步上。

把起点固化成工件之后，从“重建或使用 Loment”出发的路径上已经没有解释器，也没有 C 编译器。剩下的 Python 只在开发期判据（一致性套件、CI）与构建 / 发布脚本上 —— 每一项都写了可测量的迁移判据，而产品路径是干净的。

clang 原本站在两处必经之路上：把种子 .ll 变成 stage1，以及把每一个发射出来的 .ll 变成可执行文件。仓库里没有自己的汇编器 / 链接器，IR 到可执行文件这一段一直外包给 LLVM。现在这件事由 lomelf 接手 —— 它是第三个后端，不改冻结面里的 codegen.lomt / driver.lomt，也不动既有的两后端逐字节等价。WSL 是这条依赖的连带后果（产物是 Linux ELF，Windows 侧只能把整套工具链装进 WSL），所以“去 clang”和“去 WSL”是同一根绳子上的两段。

种子本身也有一道棘轮：门禁每次都拿参考实现重新发射一遍并逐字符比对 —— 自举产物变了而种子没跟上，门禁就红。这是“种子不许过期”。

还有一条要写明的：链条总要有第一个可执行文件，genesis 就是那个。它有来源（种子加一次 clang/lld）、有哈希、可复现 —— 但它确实是个二进制。所以 clang 并没有从这个项目里消失，它只是被从链条上拿掉了：重新铸造 genesis（python tools/loment_genesis.py --emit）仍然要一次 clang 或 WSL；只核对哈希（--check）不需要。另外 genesis 是 Linux ELF，所以这条无 clang 的路跑在 Linux / macOS / WSL 上。

还差什么（写清楚）

  • 源代码已经公开，第三方审计还没过 —— 版本 0.1.4 Pre2 已经完成（冻结面见 docs/158），且源代码已在 github.com/FujoJTOP/loment 公开；未达的 M100 是第三方审计本身。100 个里程碑口径下完成 96 个、部分 2 个（M56 LSP 宿主已就位、编辑器内人工点验待做；M92 交叉编译到 aarch64 通过但没有模拟器可验）、未开始 1 个（M39）。
  • 构建 / 发布路径还有 Python —— 用户侧工具链（格式化、文档、语言服务、包管理）与 L0 生成器都已 Loment 化，构建路径也走了两格（lomstatus、lomrel）。剩下的是构建与发布脚本这一侧：lom_spec_emit / loment_release / loment_src / loment_dist / loment_seed / loment_manual。命令面本身已经不是 Python 了——发行包里的 loment 是一个 Loment 程序（loment/tools/lomcli.lomt）。开发侧入口 python tools/loment.py 里的 bench / cov / dbg 仍是 Python 而且外调 clang，但它们是开发侧命令，不在产品路径上。
  • 内核侧只剩一项，而且它可能不是真缺口 —— 这一片原先整排标着 P7。现在：撤销由内核真正实施（M37，串口 INV_RUN … rev=2 nonrev=0）、A1–A4 断言接进内核并启动自检（M40/M50，CAP_ASSERTS n=2 bad=0 guards=2）、信任自适应域宽接口（M42）、中断与断言表接入（M33）都已完成，证据来自 compat 线 2026-09-15 的报告。唯一没翻的是 M39（与内核域模型对齐），而那次复核的结论是内核侧不缺东西：域表早已从静态初值搬进 arena、由 replay_init() 在启动时填满，是对比工具 tools/loment_caps_diff.py 还在找静态初值——那两条红是假阳性，要修的是工具。
  • 自举版比参考实现慢约 10 倍 —— 编译自身 12.8 秒，参考实现 1.2 秒。目前只记了基线与护栏（M86），没做优化。
口径检查： “自举完成”指的是上面那几项已达成；它不等于“第三方审计过了”。0.1.4 Pre2 的源代码已经公开，但 M100 的第三方审计仍是未达状态。
