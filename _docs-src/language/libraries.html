写一个 Loment 库

Loment 没有单独的库产物。一个库就是一个 .lomt 文件：首行 module，里面用 pub 标出要给外面看的项。使用者写 use，编译器把这个文件读进来，和使用方拼成一个编译单元一起编。

这带来两个后果，一个是好处一个是代价，动手前都得知道：好处是没有 ABI 要维护、没有版本兼容矩阵、没有符号导出表，改一个库使用者重编就完了；代价是顶层名字全单元共用——你叫 parse、使用者也叫 parse，那就是重名错误。

最小的一个库

库这边：一个文件，一个模块名，两个 pub 项。

loment 库 
// loment/lib/units.lomt
module units

pub const SCALE: u32 = 1000;

pub fn to_grams(kg: u32) -> u32 {
    return kg * SCALE;
}

使用方：use 之后直接写裸名字调，不写 units::to_grams。

loment 使用方 
module app

use units

fn _start() {
    let g: u32 = to_grams(3);
    // g == 3000
    syscall4(60, 0, 0, 0);
}
  • 调用是裸名字 —— 符号名本来就是平的（见下面「最硬的一条约束」），所以没有 :: 前缀这回事。
  • _start 只有使用方写 —— 库文件里不要放入口。一个单元里也只能有一个。

use 怎么找到它

写法 去哪儿找
use units 按顺序在 loment/lib/ → loment/examples/ → loment/selfhost/ → loment/tools/ 里找 units.lomt
use "lib/units.lomt" 按路径，相对当前文件或工作目录

找不到、或者同时命中多处，都报 E18。名字形式是给「装在 lib/ 里的公共库」用的；库自己的伴生文件（比如 json.lomt 与它旁边的辅助文件）要用路径形式，否则会跟着使用者的目录结构漂移。

最硬的一条约束：符号名是平的

发射出来的符号名不会被加上模块前缀：to_grams 就是 to_grams，不会变成 units_to_grams。这是刻意的——内核线按名字找入口，mangling 会把那条路打断。

代价落在库作者头上：一个编译单元里，顶层名字必须唯一——函数、结构体、枚举、常量都算。两个文件都定义 parse，编译器报 E-DUP，而且错误信息会直接告诉你「单元的发射符号是平的 (ABI)，请改名」。

所以真实的两张库，公开名字全部带前缀。

库 公开面
loment/lib/sha256.lomt SH_CNT · sha_init · sha_update · sha_final · hex_dig
loment/lib/json.lomt json_parse · json_get · json_nkind · json_emit_u32 …
loment/examples/bytes.lomt load16 · load32 · store16 · store32
注意最后一行的差别： bytes 是示例，不是给人当依赖用的，所以它的名字没带前缀。你要发一个库，就带前缀——发出去之后再改名，所有使用方都得跟着改。

为什么两张真库都收 ptr 和偏移量

看一眼真实签名，它们长这样：

loment 真实签名 
pub fn sha_update(s: ptr, p: ptr, n: u32)
pub fn json_parse(js: ptr, len: u32, arena: ptr) -> u32
pub fn load32(p: ptr, off: u32) -> u32

没有切片参数、没有按值的 struct、没有容器类型。这是三个原因叠在一起的结果，不是风格：

  • 没有标准库 —— 没有 String / Vec / HashMap，也没有内存管理。要什么自己用 alloc 从堆里划。
  • 按值传聚合目前走不通 —— 包里的自举链接器还不支持按值传 struct / enum。所以库的接口一律是 ptr、偏移量和 u32 下标。
  • bump 堆只有 64 KiB —— alloc 与 str_concat 都从它里面拿。库想省内存，就得让调用方把缓冲传进来，而不是自己分配。

第三条正是 json.lomt 的设计来源：它自己不分配，调用方给一块 arena，库在里面建节点，返回 u32 下标。想写一个能被别人用的库，这是当前最站得住的一种接口形状。

打包与依赖

一个包是一份 pkg.json。依赖写成本地路径，没有网络仓库。

json pkg.json 
{
  "name": "units",
  "version": "0.1.0",
  "deps": {
    "bytes": { "path": "../bytes" }
  }
}
bash 包管理器 
lompkg resolve pkg.json --lock lompkg.lock --write   # 解析拓扑序并写锁
lompkg verify  pkg.json --lock lompkg.lock           # 拿锁核对每个包的内容哈希
  • 依赖按拓扑序排，环会被拒 —— 同一个依赖被两个模块引用时只装一次。
  • 锁文件记的是 name → hash —— 哈希由库自己的 sha256.lomt 算出来，没有外部工具参与。
  • 退出码 —— 0 表示通过，1 表示解析或校验失败，2 表示用法错误。

写库时会踩到的坑

  • 形参最多 10 个 —— 超了会让自举阶段的编译器自己崩掉，症状是「编译这个文件时编译器死了」，而参考实现编同一份文件正常。超了就把参数打包：lompkg 里 do_div 就是把三个参数打包成一个来绕的。
  • let 必须写类型 —— 语言没有类型推断，let x = 1; 不合法。另外没有无值的 return;，要写 return <expr>;。
  • match 的臂体是块 —— 写 Kind::A => { return 0; }，不是 Kind::A => 0,。
  • 泛型调用的实参要能把类型定出来 —— pick(4, 9) 报的是「调用未定义的函数 pick」，这条消息会骗人，它不是跨模块问题。先 let a: u32 = 4; 再 pick(a, b) 就对了。
  • 结构体字面量不能直接当实参 —— f(S { a: 1 }) 会被原生后端拒。先 let x: S = S { a: 1 }; 再传 x。
  • 先定义后使用 —— 模块内不要依赖前向引用。
  • 一次只改一处 —— 一个解析错误会中止整个检查，后面的诊断一条都不出来。「没有别的错」通常只是没检查到。改完立刻跑 loment check。
  • check 通过不等于能出可执行文件 —— 按值传聚合、以及用 == 比较 struct / enum，检查器放行而原生后端会拒。库的接口避开这两个形状。

现在做不到的

  • 没有分开编译 —— 库每次和使用方一起编。大库会拖慢每一次改动的迭代，这是「拼成一个单元」的直接代价。
  • 没有版本化的 ABI —— 符号名是平的，同名即冲突，所以「同一个库的两个版本共存」做不到。
  • 没有动态链接 —— 全部静态编进最终产物。
  • 只有本地路径依赖 —— pkg.json 不认识版本区间，也没有中心仓库。谁依赖谁、用哪个版本，目前靠约定和锁文件。
一句话总结接口设计： 在没有标准库、没有按值聚合、堆只有 64 KiB 的前提下，当前最站得住的公开接口是 ptr 加偏移量、缓冲由调用方传进来。这也是仓库里两张真库长成那样的原因——不是因为风格，是因为约束。
