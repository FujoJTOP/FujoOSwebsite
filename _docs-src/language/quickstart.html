Loment 快速上手

Beta。 Loment 目前是 0.1.3 Alpha：100 个里程碑完成 79 个，语言尚未冻结。下面的命令今天可用，但语法与参数在 1.0 之前都可能变。本页每一条命令与输出都是在仓库里实跑得到的，不是示意——如果哪条跟你跑出来的不一样，那是我们其中一方的版本不对，请以你的输出为准。

前置

需要 什么时候需要
Python 3 始终。参考编译器本身就是一个纯 Python 程序，没有 pip 依赖——这一点在项目里不是妥协，是刻意的。
rustc 只有要跑程序时。第一版编译器是转译器：Loment → Rust，再用 rustc 编译执行。
clang + lld 只有走原生后端（LLVM IR），或要产出跑在 FujoOS 用户态里的 ELF 时才需要。

六十秒

在仓库根目录下。最快的一次成功只需要一条命令——写一个带 test_ 函数的文件并跑它。

bash 跑内建测试 
python tools/loment.py test hello.lomt

PASS test_double_5
PASS test_double_0
RESULT: 2/2 PASS

这条命令之所以最快，是因为它替你做了三件容易忘的事：转译成 Rust、套一个 main 调用每个 test_* 函数、用 rustc 编译并执行。失败时它会以退出码 1 结束。

一个最小程序

存成 hello.lomt。语法是 Rust 的严格子集，所以如果你写过 Rust，这里没有新东西要学——新东西在能力域那一层。

loment hello.lomt 
module hello

fn double(x: u32) -> u32 {
    return x * 2;
}

fn test_double_5() -> bool { return double(5) == 10; }
fn test_double_0() -> bool { return double(0) == 0; }

module 是必需的。其余与 Rust 一样：fn、显式类型、let、while、for i in 0..n、match。test_*() -> bool 是约定，不是语法——工具链按名字找它们。

一条会立刻绊到你的规矩

你想把程序转译出来，很自然会这么写：

bash 会被拒绝 
python tools/lomentc.py hello.lomt --emit-rust hello.rs

[ERR] M46: 编译器强制导出形式对象 —— 需同时给出 --emit-potato PATH

这不是 bug，是设计：编译器不允许只产出目标代码而不产出形式对象。正确写法是两个一起给。

bash 转译 + 强制导出 
python tools/lomentc.py hello.lomt \
    --emit-rust hello.rs \
    --emit-potato hello.potato.json

[OK] hello.lomt -> hello.rs (1241B)
[OK] hello.lomt -> hello.potato.json (815B)
为什么值得别扭一下： 同一个约束在三个层面都不可关闭：编译器内部有错即编译失败；CLI 上要 emit 目标就必须同时 emit 形式对象；仓库里要求每个示例都带一份逐字节一致的对象。这是为了让「内核读得懂这段代码被允许做什么」成为常态而不是努力。见 Potato 形式对象。

形式对象：让机器看懂这段代码

上一步顺带产出的 hello.potato.json，就是 Potato 形式对象。它不描述代码「长什么样」，只描述「它声明了什么」：

json hello.potato.json 
{ "potato": "v1", "unit": "hello", "language": "loment",
  "capabilities": [],
  "functions": [
    { "name": "double", "params": [{"name": "x", "type": "u32"}], "ret": "u32" }
  ],
  "guards": 0,
  "excluded": [] }

用独立校验器验它——注意这个词：校验器不 import 编译器的任何代码。

bash 校验 
python tools/potato.py validate hello.potato.json

[OK] hello.potato.json: 形式对象合法

能力域：真正的新东西

你想让某段代码只能碰磁盘块 0 到 4，并且可以随时被收回。这不是一个运行时检查函数，而是一条语言声明：

loment native_cap.lomt 
capability blk_write : disk[0..4] revocable

fn write(slot: u32) -> u32 {
    guard blk_write(slot);   // 越界：字面量在编译期拒绝，运行期落到 trap
    return slot;
}
一件事，四处生效 发生时机
越界字面量直接编译失败编译时
动态越界落到运行期 trap运行时
每次 guard 落一条审计计数每次使用
域描述表写进形式对象编译时

还有一个配套的声明叫 excluded，用来明确写出「本单元不申请哪些能力」。它同样会进入形式对象的 excluded 字段——也就是内核能读到你的边界声明。细节见 能力域即语言构造。

出错了会看到什么

诊断是分好类的，每一条都带修复建议——不是一句「语法错误」然后让你自己找。

bash 诊断 
python tools/loment.py diag loment/selfhost/neg/arity.lomt

E003 [实参数量不符] 8: g 需要 1 个实参，得到 2
      建议: 对照函数签名补/删实参；方法调用的 self 不计入实参。

错误分成 E001–E013 十三类，每一类都有一条对应的反例——也就是说这些分类不是文档里的一张表，是真的会触发的代码路径。

工具链一览

统一入口是 tools/loment.py。它自己不编译，只是把活分派给对应的工具。

命令 做什么
loment test FILE跑所有 test_*() -> bool 函数
loment diag FILE [--json]错误分类 + 修复建议
loment fmt FILE...格式化（幂等：两次结果相同）
loment ir FILE [--objdump]看 IR，或连同机器码一起看
loment cov FILE [--call F]IR 级块覆盖率
loment bench FILE [--n N]Rust 路径与 IR 路径对比
loment dbg FILE [--fn F]符号化：按函数列源行
loment build DIR [--out DIR]增量构建（冷 82.6 ms → 热 9.0 ms）
loment doc FILE [--out]从源码生成 API 文档
loment pkg ...包管理：依赖解析 + 校验和
loment lsp语言服务（编辑器补全 / 跳转 / 诊断）

另一条线：L0

上面讲的都是 L1（语言本体）。还有一条更靠底下的线：.lom 文件是布局与契约的单一真源，由 lomc 生成 Rust / C / Python / JSON。

bash L0：一处声明，多处生成 
python tools/lomc.py lom/fuc.lom --emit-rust  out.rs \
                                 --emit-c     out.h \
                                 --emit-python out.py \
                                 --emit-json   out.json

# 或者不落盘，只核对磁盘产物是否与生成结果一致：
python tools/lomc.py lom/fuc.lom --check

L1 的源文件可以 use 一个 L0 文件——声明来自 L0，行为来自 .lomt。这是「Loment 是 .lom 的超集」这句话的实际含义。见 L0 单一真源。

现在还不能做什么

  • 语言还没冻结 —— 0.1.3 Alpha。M96（1.0 冻结）与 M100（发布审计）都未达，所以在 1.0 之前可能出现破坏性改动。
  • 原生路径要 Linux 或 FujoOS —— --emit-llvm 产出的 IR 按 x86_64-unknown-linux-gnu 链接。在 Windows 上用转译路径（本页所述）即可，两者能力不完全等价。
  • 自举还差两件事 —— 自举版编译器的符号表是全单元扁平的（兄弟模块同名私有函数会撞名），且子集检查器会把合法程序判错。见 自举。
  • 面向开发者的首个版本尚未发布 —— 按计划 9.20 面向开发者。在那之前，本页描述的是仓库当前状态，不是已发布产品。
